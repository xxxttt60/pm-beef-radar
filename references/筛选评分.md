# 筛选评分（PM 产品版）

用于评估「产品经理可二次包装」的 AI Agent 产品。**推荐对象始终是 Agent 产品**：任何模式下都必须通过 Agent 四件套门槛，普通 B 端工具（CRM、工单、BI、项目管理等无 Agent 能力者）不属于本 skill 的推荐范围。

## 项目定位

- `通用场景 Agent`：面向 C 端或通用场景的 Agent 产品（知识库问答、学习/面试助手、写作/办公 Agent、生活助理等），PM 可做场景化 / 垂直化改造，形成 0-1 项目叙事。
- `B 端场景 Agent`：面向企业业务流程的 Agent 产品（智能客服、销售/SDR、招聘/HR、数据分析/ChatBI、运营/营销 Agent 等），PM 可做行业化 / 流程化改造，支撑业务闭环叙事。

推荐模式必须由用户明确选择；未指定时先反问，不进入评分。

## 推荐模式评分偏好

- `ai-product-only`：必须有可体验的产品形态（按「产品形态分级」，不要求自带 UI）+ 主流程 + Agent 四件套至少 2 项（≥3 项优先排序）；纯框架 / SDK / 工具链一律淘汰。
- `b2b-only`：只保留 B 端业务场景的 Agent 产品；无 Agent 能力的传统 B 端工具（CRM、工单、BI、项目管理）一律淘汰，不得以「可接 AI」为由保留；默认排除 IoT / 硬件类。
- `mixed`：必须跨「通用场景 Agent」和「B 端场景 Agent」两类；两个项目不得共用同一简历卖点。
- `safe-mode`：加大"Docker 一键起、依赖少、文档清晰、7 天可产出"的权重；需要 GPU / 多模型账号 / K8s 的项目降权。
- `vertical-mode`：加大"业务场景可映射到用户垂直行业"的权重；无行业映射价值的项目降权。

## 产品完整度门槛（替代研发版的业务型 Agent 门槛）

候选必须命中以下至少 2 项（README probe + 描述 + topics 判断；≥3 项加分）：

- 产品形态可体验：自带 UI / 桌面端 / 嵌入现有平台的机器人 / API 服务 + 交互文档（按「产品形态分级」评估）。
- 可体验：有 demo / screenshots / hosted 版 / sandbox。
- 业务场景：能命名成某个业务产品（如"AI 学习助手""智能客服 Agent"）。
- 多用户 / 权限：auth、角色、团队、多租户。
- 可部署落地：docker / 一键部署 / 清晰 quickstart。

README probe 只用于筛选和定位，不能作为最终"产品拆解 / 改造方案"的唯一证据。

## 三层判定：平台 / 框架 / 应用（AI 产品方向第一道筛）

在 Agent 能力门槛之前，先判断候选属于哪一层：

| 层级 | 特征 | 处理 |
| --- | --- | --- |
| 平台 / 构建器 | 定位是「搭建 Agent 的平台」：builder / platform / studio / workflow builder / LLMOps / 低代码编排；本身没有具体业务实体 | **不得作为项目主体**，只能作为底座（技术选型） |
| 框架 / SDK | 库级抽象，无产品形态 | 淘汰 |
| 应用 | 有业务实体与闭环（坐席、会话、工单、订单、审批、知识库），有角色权限 | 可作为项目主体 |

判定方法：读 README 首屏与 docs 目录，确认是否存在业务实体（用户 / 工单 / 会话 / 订单 / 审批）与角色权限；只有「工作流画布 + 知识库 + 应用发布」三件套的，判定为平台。

选平台作底座时的强制要求：必须同时定义**应用层改造范围与证据**——工具 schema、评测集、兜底链路、成本统计、badcase 记录；缺任一项则淘汰，不允许写「基于 XX 平台搭建」充当项目成果。

## Agent 能力门槛（AI 产品方向必查）

面向 AI 产品经理岗位时，仅「有可体验形态 + 有业务场景」不够，候选（应用层主体或应用层改造）必须具备 Agent 能力四件套中的至少 2 项：

- 多轮对话与上下文管理（能追问、能改写意图）
- 知识检索 RAG（数据来源、分块、召回链路可查）
- 工具调用 / 插件 / MCP / 工作流节点（能触达外部数据与动作）
- 会话或用户记忆（跨轮 / 跨会话）

判定规则：

- 四件套门槛是**必要非充分条件**：通过门槛只代表"不是纯 RAG 问答壳"，短名单人工复核必须再问一句「**除 RAG 问答之外还有什么**」——没有工具编排、业务实体（坐席/工单/订单/审批）、人机协作（转人工/确认）其中至少一项的，淘汰（脚本 `BEYOND_RAG_GATE` 做关键词初筛，人工复核确认）。仅"LLM + 知识库 + 聊天窗"的项目（哪怕是活跃大厂出品）属于同质化最严重的类型，不作为主推项目。

- 传统客服台、工单系统、BI 工具、项目管理工具**默认归为「宿主平台」**，即使接了 AI 插件，也不能单独作为 Agent 项目推荐。
- 宿主平台只能作为「真实落地背景」出现在叙事里（如"在既有客服台上挂 Agent"），Agent 主体必须是候选项目自身具备的能力。
- 四件套只命中 1 项或全部缺失的项目，在**任何模式下**一律淘汰，不得用"可以改造"作为保留理由。
- 记忆能力普遍是开源项目的短板，允许作为改造点保留，但必须明确写出改造工作量。

## 企业落地性门槛（B 端项目必查，PM 版核心）

**适用范围**：B 端场景 Agent **必须通过**本门槛，不通过即淘汰——推荐一个企业里落不了地的 B 端项目，面试追问「怎么落地」时叙事即崩塌。通用场景 Agent 不做硬淘汰，但短名单必须标注企业落地约束。脚本判定 B 端采用**双重确认**：所有分桶均来自 B 端查询桶 + 文本含 B 端业务场景信号（customer support / sales / recruiting / enterprise 等）——B 端桶偶尔捞出「个人助手」类项目，按通用处理只标注约束；判定宁漏杀交人工复核，不误杀。

### 红线（脚本 `ENTERPRISE_REDLINE` 初筛 + 人工复核确认，B 端命中即淘汰）

| 红线 | 特征 | 为什么落不了地 |
| --- | --- | --- |
| 代操作企业系统 | computer-use / browser-use，要拿账号在企业系统上代执行操作 | 权限归属、操作审计、责任边界三道关过不了安全评审；除非收窄成只读检索，否则无试点路径 |
| 纯个人工具定位 | local-first / personal notes / 个人助手类 | 数据不落中心、无协同、无权限、无审计，企业 IT 不接受，没有采购理由 |

红线判定是**排除性**的：脚本只做关键词初筛，README 未探测到时红线不触发，宁漏杀交人工复核，不误杀。

### 落地性四问（短名单人工复核，B 端项目逐项过）

1. **场景真实性**：是否对应企业每天都在发生的真实消耗（取数工单、工单流转、简历初筛）？还是「看起来有场景」的自嗨？
2. **ROI 可量化**：能否说出硬指标（取数响应从小时级到分钟级、某环节人力下降）？只能说「效率提升」而给不出量化口径的，降权。
3. **合规安全**：能否过企业安全评审？只读查询容易过；涉及写操作、数据出域、代操作的，要有明确的收窄方案（如限定只读主题域）。
4. **替代风险**：是否会被 BI / 客服 / 协作厂商的内置 AI 能力直接吃掉？零集成即可试点但无独立采购理由的（护城河浅），降权谨慎推荐。

四问中第 3 问不过且无收窄方案 = 淘汰；第 1、2 问不过 = 淘汰；仅第 4 问不过 = 降权，并在短名单注明「替代风险」。

### 通用场景项目的处理

不硬淘汰，但必须在短名单中**标注企业落地约束**并给出叙事调整建议——例如 computer-use 类项目不讲「个人助手」，改讲「Agent 操作企业系统的权限 / 审计 / 责任边界设计」，主动交代落地约束反而更可信。


## 用户画像偏好

- 转型期 PM（无 AI 项目经历）：偏向 safe-mode 或 ai-product-only，先保证跑通和产出。
- 有垂直行业积累（以用户自述行业为准，skill 不预设）：偏向 vertical-mode，项目必须能吃到行业认知红利。
- 目标 AI PM：AI 产品优先，且项目必须能讲到评测 / 数据 / 迭代层。
- 目标 B 端 / 平台 PM：B 端场景 Agent 优先，且必须能讲清 Agent 对既有流程的改造价值（替代/增强/兜底），而不是「又一个聊天机器人」。
- 时间预算少于 1 周：建议 safe-mode，但不得未经确认自动切换。

## 多样性协议

1. 至少覆盖 4 个分桶和 6 组查询词。
2. 候选池尽量达到 15-30 个仓库（Agent 产品稀缺，不足 10 个时说明原因并补充查询）。
3. 每桶保留前 3-5 个，不按 star 数取前几名。
4. 默认跨分桶推荐；`mixed` 必须跨两类。
5. 分数接近时，优先选择：业务场景更清晰、更容易跑通、改造空间更大、更贴合用户垂直行业的项目。
6. 对"AI PM 面试烂大街项目"（通用 chatgpt 套壳、todo、博客系统）降权。
7. 同一轮推荐中，不得让多个项目依赖同一卖点（都讲"接入大模型"或都讲"工单流转"）。

## Star 权重与反热门偏置

- 500-5k star 是甜蜜区间：有社区验证、又不至于面试官人手一个。
- 1k+ star 即入围正式候选池，与更高 star 项目同等评估。
- 20k+ star 项目不自动加分；若同质化强或反复出现在推荐中，触发热门惩罚。
- 搜索组合使用业务关键词 + star 区间（如 `stars:500..5000`）+ 更新时间，不用全局 `sort=stars`。
- 最终推荐默认最多保留 1 个 20k+ 项目。

## 分桶

通用场景 Agent 分桶：知识库/RAG 问答 Agent、学习/教育 Agent、面试/求职 Agent、写作/办公 Agent、生活/兴趣 Agent、研究/投研 Agent。

B 端场景 Agent 分桶：智能客服 Agent、销售/SDR Agent、招聘/HR Agent、数据分析/ChatBI Agent、运营/营销 Agent、企业知识/内部问答 Agent、代码/运维 Agent。

Agent 产品包装优先信号：

- 有可命名的产品形态和目标用户。
- 有主流程闭环（如：上传文档 → 提问 → 带引用回答 → 反馈；提交工单 → 分派 → 处理 → 关闭 → 评价）。
- 有角色与权限（管理员 / 普通用户 / 团队）。
- 有数据对象与状态（会话、工单、任务、报表）。
- 有扩展点（API、MCP、插件、webhook），支撑改造叙事。
- 有可观测与可评测的可行性（能拿到输出日志、能建评测集、能统计成本），支撑面试分水岭层叙事：评测体系、不确定性兜底、成本账——这是 AI PM 面试真正的分层线，只有第一层硬门槛（能跑、多轮、RAG、工具调用）的项目只能算 60 分候选。
- issues 里有真实痛点，可转化为需求池素材。

默认淘汰：

- 纯框架 / SDK / library / toolkit。
- awesome list、prompt 集合、教程复刻、课程 demo。
- 无产品形态的纯库 / 框架（要用户自己写壳）；纯 CLI 仅在业务场景强贴合时保留并降权（见「产品形态分级」）。
- IoT / 嵌入式 / 硬件类（除非用户明确要求该方向）。
- 文档混乱、跑不起来、长期未维护的仓库。

## 评分模型

```text
总分 = 产品形态可体验度
     + 业务场景真实度
     + 企业落地性（B端必查：场景真实性/ROI可量化/合规安全/替代风险，见落地性门槛）
     + 包装空间（垂直化/改造潜力）
     + 体验门槛（跑通成本，越低越高分）
     + 文档与社区质量
     + 用户画像匹配度
     + 推荐模式匹配度
     + 叙事可写性（能否写出责任层级 + 指标闭环）
     + 不确定性管理设计空间（能否建评测集 / 兜底链路 / 成本统计）
     + star 社区验证弱加分（1k 封顶）
     − 热门惩罚
     − 纯工具/框架惩罚
     − 复杂度过高惩罚（跑不通 = 直接淘汰）
     − 模式冲突惩罚
     − 企业落地性惩罚（通用项目命中红线 -2，B端命中即淘汰）
```

## 硬性淘汰

- 无 Agent 能力的普通 B 端工具（CRM、工单系统、BI、项目管理、低代码平台）——不属于本 skill 推荐范围，只能作为宿主/底座背景。
- 纯框架、SDK、工具库、prompt 集合、awesome list（无产品形态：不提供可运行的服务或应用，只是要用户自己写壳的代码）。
- Agent 平台 / 构建器 / LLMOps 工具链（builder、studio、workflow 画布类）作为项目主体时。
- **不能在企业实际落地的 B 端项目（企业落地性红线：代操作企业系统、纯个人工具定位；脚本 `ENTERPRISE_REDLINE` 初筛，人工复核确认）。**
- 无任何可体验形态且无法评估跑通路径的项目。
- todo / 博客 / 单页 chat 套壳等教程级项目。
- 文档弱、长期无人维护的仓库。
- IoT / 硬件类（除非用户明确要求）。

## 产品形态分级（判据：可体验，而非必须有 UI）

「无自带前端」不是缺陷，判据是**用户能否端到端体验主流程、能否现场演示**：

| 形态 | 示例 | 处理 |
| --- | --- | --- |
| 自带 Web UI / 桌面端 | 知识库问答应用、客服台 | 最优，演示成本最低 |
| 嵌入现有平台 | 微信/Telegram/Slack/Discord 机器人 | 合格，前端即平台本身；需注意平台合规风险 |
| API 服务 + 交互文档（Swagger/Playground） | headless Agent 服务 | 合格但降权；短名单必须注明演示形态与演示成本 |
| 纯 CLI | 命令行 Agent | 弱，仅当业务场景强贴合时保留并降权 |
| 纯库 / 框架 | 需要用户自己写壳 | 淘汰 |

演示路径不清晰、或演示需要自建完整前端的，视为「无法现场演示」，降权或淘汰；`safe-mode` 下只接受前两种形态。

## 包装质量门槛（PM 版核心）

最终推荐的项目必须满足：

1. 能命名成一个业务产品（如"面向某行业的智能问数助手"，行业随用户输入变化），而不是"一个 RAG 项目"。
2. 能写出 0-1 改造路线：垂直化数据 / 场景 / 功能 / 指标至少各 1 条。
3. 能写出指标闭环：北极星指标 + 过程指标（如解答率、转人工率、完课率）。
4. 能被面试追问 3 层：为什么选这个场景 → 为什么这样设计 → 上线后怎么迭代。
