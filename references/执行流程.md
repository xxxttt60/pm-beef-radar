# 执行流程（PM 产品版）

在筛选可二次包装的 AI Agent 产品并生成 PM 简历包时，按以下流程执行。

## 默认假设

- 用户未说明背景时，默认为转型期 / 初级产品经理，目标 AI PM 或 B 端产品岗。
- 默认输出语言：中文。
- 推荐模式没有默认值，必须由用户明确选择；缺失时先完整列出五种模式反问，禁止自行按 mixed 或其他模式执行。

## 输入解析

1. 先检查用户是否明确指定推荐模式：`ai-product-only`、`b2b-only`、`mixed`、`safe-mode`、`vertical-mode`。
2. 没有指定则立即停止后续流程，用固定话术完整展示五种模式并反问。
3. 用户回复模式后，提取用户画像：目标岗位、垂直行业、体验能力（能否跑 Docker / 调 API / 读代码）、时间预算、项目偏好、避开方向、输出需求。
4. 画像信息不足可按默认画像继续，但必须标注"按默认画像处理"。

## 推荐模式执行规则

- `ai-product-only`：最终推荐只保留通用场景 Agent 产品（知识库问答、学习、面试、写作/办公等）；必须有可体验的产品形态（自带 UI / 嵌入平台 / API 服务 + 交互文档，见 筛选评分.md 产品形态分级），不得推荐框架、SDK、prompt 集合、单页 chat 套壳。
- `b2b-only`：最终推荐只保留 B 端业务场景的 Agent 产品（智能客服、销售/SDR、招聘/HR、数据分析/ChatBI、运营/营销等）；无 Agent 能力的传统 B 端工具（CRM、工单、BI、项目管理、低代码）一律淘汰，不得以「可接 AI」为由保留；默认排除 IoT / 硬件 / 嵌入式类。
- `mixed`：至少一个通用场景 Agent + 一个 B 端场景 Agent；两个项目不得依赖同一简历卖点。
- `safe-mode`：优先 Docker 一键部署、文档清晰、7 天内可跑通并产出拆解 + PRD 的 Agent 产品；降低需要 GPU、多模型账号、K8s 集群的项目权重。
- `vertical-mode`：优先业务场景能映射到用户自述目标行业的 Agent 产品；输出时必须写明行业映射关系（用户提供的行业与项目场景如何对接，skill 不预设行业，映射逻辑由用户输入驱动）。

## 执行步骤

1. 确认推荐模式；没有则先反问并停止。
2. 提取用户画像。
3. 广泛搜索：至少 6 组查询、覆盖 4 个以上分桶；优先运行 `search_pm_candidates.py`。
4. 构建候选池：目标 15-30 个仓库（Agent 产品稀缺，实际搜到的合格候选可能更少，少于 10 个时需说明原因并补充查询），记录链接、星标、语言、更新时间、描述、README probe 状态、分桶、初筛分和理由。
5. 筛选打分：按 `筛选评分.md` 执行——先做三层判定（平台 / 框架 / 应用，平台只能当底座、框架淘汰），再过 Agent 能力门槛（多轮上下文 / RAG / 工具调用 / 记忆，≥2 项）和「除 RAG 外」门槛（工具编排 / 业务实体 / 人机协作 ≥1 项），最后过产品完整度门槛（≥2 项）；传统客服台、工单、BI 等宿主平台不得作为 Agent 项目进入短名单；B 端项目还要过企业落地性门槛（`ENTERPRISE_REDLINE` 红线初筛 + 人工按落地性四问复核：场景真实性 / ROI 可量化 / 合规安全 / 替代风险）；每桶保留前 3-5 个。
6. 短名单确认：输出 3-4 个拟深入项目，包含链接、分桶、建议包装方向（0-1 叙事定位）、选择理由、主要淘汰理由和待拉取仓库列表；B 端项目必须附落地性四问结论（或淘汰原因），通用项目必须标注企业落地约束（如 computer-use 类需换「安全边界」叙事）；用户确认前不得拉取。
7. 强制拉取仓库：用户确认后运行 `pull_github_repos.py`；不得用 GitHub raw/API、网页、README 缓存或模型记忆替代本地仓库。
8. 核实 manifest：只允许 `status=cloned` 的仓库进入验证；失败候选直接淘汰。
9. 产品体验验证：基于本地仓库完成以下动作——
   - Agent 四件套打勾：多轮上下文 / RAG / 工具调用 / 记忆，逐项标注「有 / 无 / 待验证」及证据位置；缺失项只能作为改造点，不得当作已有能力；
   - 读 README / docs：确认产品定位、目标用户、核心场景、部署方式；
   - 读部署配置（docker-compose / env / 安装脚本）：评估本地跑通成本，safe-mode 下必须给出跑通步骤；
   - 读目录结构：识别功能模块、角色权限、数据模型线索；
   - 结合 GitHub issues（可联网查看）：提取真实用户痛点，作为需求池素材。
10. 产品证据点：每个最终项目至少提取 5 个证据点，例如——目标用户与场景、核心主流程（截图/步骤）、角色与权限设计、数据对象与状态流转、集成与扩展点（API/MCP/插件）、部署与运营成本、issues 中的真实痛点、商业模式线索。输出时标注证据来源（文件 / 目录 / issue 链接）。
11. 包装方向设计：为每个入选项目产出「0-1 改造路线」——垂直化 / 场景化改造点、新增功能建议、指标定义、试运行方案；必须区分已有能力与建议改造。
12. 面试三层对照：按 AI PM 面试标准逐项自检——第一层硬门槛（能跑通、多轮、RAG、工具、边界认知）、第二层分水岭（评测集、badcase 七步归因、不确定性兜底、成本与延迟、记忆分层、人机边界）、第三层加分项（行业 know-how、数据治理、POC→试点链路、可观测性、合规权限、商业价值）。缺项写进改造清单并标注优先级（P0/P1/P2）。
13. 生成输出：按 `输出模板.md` 生成简历包文稿；简历条目按 `简历写法.md` 撰写。

## 强制仓库拉取

- 脚本：`references/pull_github_repos.py`。
- 时机：短名单确认后、生成任何"产品拆解 / 改造方案"之前。
- 淘汰规则：未执行脚本、脚本失败、manifest 缺失、状态不是 `cloned`、无法提取 ≥5 个产品证据点，均不得进入最终推荐。

## 输出要求

- 每个推荐项目给出链接和包装方向。
- 必须有候选池表、推荐模式说明、多样性说明和可替换项目。
- 必须区分「已有能力」「建议改造」「可写入简历」。
- 简历条目要具体、能被追问；产品证据统一放"产品验证摘要"，正式叙述中写清实现边界，不得把未实现内容写成已有成果。
- 必须输出产品验证摘要：读了哪些文档 / 目录 / 配置，跑通了什么，issues 里发现了什么。
- 必须输出 Agent 四件套打勾表，以及面试三层对照表（每层标注：已具备 / 待补 / 改造动作）。
- `safe-mode` 必须给 7 天落地计划；`vertical-mode` 必须给垂直行业映射和叙事升级路径（"我做了一个 Agent" → "垂直行业 AI 落地"）。
